# FrameTrail — working agreement

Read this first in every session. It is the single source of truth for direction, rules and status. Keep it short and current: update **Status** and **Decision log** when something real changes; do not add history essays, receipts or handoff files.

## What FrameTrail is

A native Windows desktop app (C++20, Qt, FFmpeg, ONNX Runtime, SQLite) that analyses images, video files and a webcam. It detects objects, tracks them over time, records when each appearance starts and ends, counts line crossings, and exports results. Private, single-user project. It will not be sold or shared.

## The goal

**One RF-DETR model that recognises about 600 everyday object categories well enough to be the app's main detector.**

Concretely, the first target is a fine-tuned RF-DETR that:

1. Covers the Open Images everyday vocabulary (pilot: about 100 classes, then about 600).
2. Beats the YOLOv8 Open Images model already in the app on the same held-out Open Images test images (Open Images-style mAP@0.5).
3. Stays at least as good as today on people and vehicles.
4. Runs inside FrameTrail (ONNX, GPU via DirectML, CPU fallback).

"Anything you throw at it" beyond the trained vocabulary is a later, separate open-vocabulary mode. It is not a requirement for the main model.

## Strategy in one paragraph

Train the whole RF-DETR model (not single classifier rows) on large public datasets (thousands of images per class), measure with a standard metric on large held-out sets, and iterate in a few meaningful GPU runs instead of many tiny diagnostics. Open Images V7 first, because its 600-class vocabulary already matches the app. Later, add Objects365/LVIS for rare classes, fill missing labels with a teacher model, and build a small test set from the user's own videos.

## Road to a usable model (plan of 2026-11-11)

**What "good" means, fixed in advance.** Three held-out yardsticks that are never trained or tuned on:

- **A. COCO val2017** (5,000 photos in which every object of 80 everyday types is labelled). AP@0.5, and at the app's confidence setting the share of objects found and the share of boxes right, per type and per object size. Labels are complete, so misses and false boxes both count. YOLOX-S, the stock RF-DETR and our models are scored by the same script.
- **B. Open Images test** (16,788 photos): breadth over about 580 types, mAP@0.5 as before.
- **C. Video**: reviewed appearances on clips. The 12 Pexels clips are a practice set (problems were diagnosed on them); a second set is kept unopened until a model is final.

The footage check (agreement with YOLOX-S) and by-eye samples are diagnostics, never targets: chasing them would train a copy of YOLOX-S.

**Done** (the model becomes the default): on A it finds more than YOLOX-S at an equal or higher share right, at one setting; B stays at 0.69 or above; it wins review on the unopened clips; at most about 60 ms per frame on the laptop GPU.

**Levers, largest first.**

1. Fully labelled photos next to Open Images (COCO train, later Objects365). Open Images leaves most objects unlabelled, which taught the model doubt about everyday objects; complete labels teach the opposite.
2. Partial-label training (`--unverified-weight`, `training/missing_labels.py`): every image states which classes it vouches for, and the rest are not pushed towards "absent". This is also what lets datasets with different label sets train together.
3. More photos: 38,881 so far, against about 1.7 million available. Stored downscaled, so they fit Kaggle's disk.
4. COCO types the model knows only under an Open Images name (corrected 2026-11-12): cow = Cattle, donut = Doughnut, potted plant = Houseplant, dining table = Table, sports ball = Ball, frisbee = Flying disc, skis = Ski, remote = Remote control, keyboard = Computer keyboard, mouse = Computer mouse, microwave = Microwave oven, hair drier = Hair dryer. They are trained; yardstick A shows most work (cow 0.69, frisbee 0.84) and four are weak (cup 0.17, dining table 0.12, potted plant 0.23, donut 0.24). COCO's boxes go into these classes. Only cup has no class of its own (Open Images has just Coffee cup and Mug) and gets one.
5. Model size and input resolution for small objects, decided from A's by-size numbers against speed.

Not levers: confidence thresholds, score rescaling, per-clip tuning, hand-written class-pair patches.

**Steps** (1 and 2 done on 2026-11-12). (1) Yardstick A on the laptop for YOLOX-S and round 3: where we really stand, by type and size. (2) Mixed-dataset pipeline (COCO in our format with its vouched-for classes, the missing types, downscaled storage), rehearsed locally. (3) Round 4 on Kaggle: Open Images plus COCO train with partial-label loss; success criteria on A, B and C written down before it starts; the stock RF-DETR is scored on A in the same session. (4) Measure, then choose between more data, a larger model and a paid GPU run (the $10-50 is kept for one long run once the recipe has proved itself on free hours).

Open question, still unmeasured: whether fine-tuning on Open Images lost skill that the COCO-pretrained starting weights had. The stock RF-DETR is not on the laptop; it is scored on A in the round 4 session.

## Rules that keep us on track

- **Measure, don't argue.** Every training run ends with `training/evaluate.py` metrics on held-out test images. A claim about model quality needs a metrics file behind it.
- **Use public splits.** Train on Open Images *train*, select checkpoints on Open Images *validation*, report on Open Images *test*. Never train on validation or test images.
- **Respect missing labels in evaluation.** Open Images labels are not exhaustive. The evaluator only scores a class on images where that class was human-verified (present or absent). Detections of unverified classes are ignored, not counted as false positives.
- **Big levers first.** More and better data, full fine-tuning and a bigger model before loss tweaks. Do not hand-curate dozens of photos or sweep tiny hyperparameter grids.
- **Lightweight provenance.** Each run directory holds its config, dataset manifest, git commit, logs, checkpoints and metrics. That is enough; no receipts, seals or authorization files.
- **Data and weights stay out of Git** (`data/`, `runs/`, `*.pth`, `*.onnx` are ignored). Only code, configs, class lists and small result summaries are committed.
- **Keep the app working.** Do not break the existing analysis, save, export or playback flow when integrating a new model. YOLOX-S stays the default until a new model clearly beats it on the user's footage.
- **Don't invent facts.** If something is not verified (cluster limits, timings, accuracy), say so and check it. Write estimates as estimates.

## Decision log
- 2026-11-12: How COCO joins the training set. A COCO box goes to the existing class that means the same thing, not to the app's separate COCO-named category (cow to Cattle, not a second "cow" class), so one object keeps one label; only cup gets a new class, because Coffee cup and Mug do not cover it. "tv" boxes are not used (televisions and monitors are separate classes here and COCO does not say which), and a COCO photo never counts as "no Table" (ours includes desks). Narrower classes are unknown where their type is present and absent where it is not. Round 4 uses no teacher boxes: COCO's human labels cover the same classes better, and it keeps the model from being a copy of YOLOX-S. All usable COCO photos rather than a capped subset: more distinct photos for the same GPU hours, and Open Images photos per epoch are unchanged, so breadth is not starved. It starts from round 3, not from the COCO weights: 515 classes would otherwise have to be relearned inside one week's free hours.
- 2026-11-11: Model quality is judged on three fixed held-out yardsticks (COCO val2017 with complete labels, Open Images test, reviewed video), not on agreement with YOLOX-S, which stays a diagnostic. Round 4 is therefore not "round 3 plus a loss switch" but the first mixed-dataset run (Open Images plus COCO train, partial-label loss); a loss switch alone would have been judged on the 12 clips it was diagnosed on.
- 2026-11-10: The trained model's scores are corrected by a per-class table next to the model, fitted on validation images, not by retraining and not by per-class thresholds in the app: one confidence setting keeps its meaning ("chance the box is right") for every class and for Combined's merge by confidence, per-class AP and mAP are unchanged (the curves are monotone), and a refit needs no GPU. Two parameters per class with a pull towards the all-class curve, because most classes have under 30 validation images. A sidecar file, not baked into the ONNX, so it can be refitted or removed without an export; the cost is that a table can be left next to the wrong model, which `install-model.ps1` guards.
